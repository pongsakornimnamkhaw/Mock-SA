# แบบออกแบบหน้าบัญชีพนักงานระบบหลังบ้าน

วันที่: 10 กันยายน 2569

## เป้าหมาย

เพิ่มหน้า “บัญชีของฉัน” สำหรับผู้ใช้ระบบหลังบ้าน เพื่อดูข้อมูลบัญชี แก้ไขข้อมูลที่ได้รับอนุญาต เปลี่ยนรหัสผ่าน และตรวจสอบกิจกรรมที่ตนเองทำในระบบ พร้อมกระบวนการขอรีเซ็ตรหัสผ่านที่ผู้ดูแลระบบเป็นผู้อนุมัติ โดยคงพฤติกรรมของหน้าจอและ API เดิมไว้ให้มากที่สุด

## ขอบเขต

- ผู้ใช้ระบบหลังบ้านทุกคนเข้าหน้าบัญชีของตนเองได้จากส่วนชื่อพนักงานด้านล่างของแถบเมนู
- หน้าแบ่งเป็น 3 แท็บ ได้แก่ ข้อมูลบัญชี ความปลอดภัย และประวัติการทำงานของฉัน
- บันทึกและแสดงกิจกรรมที่เกิดหลังนำระบบใหม่นี้มาใช้
- ประวัติเก่าจะแสดงได้เฉพาะรายการที่มีรหัสผู้กระทำบันทึกไว้อย่างถูกต้อง
- เพิ่มประเภทบุคลากรสำหรับบัญชีหลังบ้าน โดยไม่เปลี่ยนความหมายของ `UserType`
- เพิ่มกระบวนการขอรีเซ็ตรหัสผ่านโดยใช้คำร้องและการอนุมัติจากผู้ดูแลระบบ

## ประเภทบัญชี

`UserType` ยังคงใช้แยกลูกค้าออกจากผู้ใช้ระบบหลังบ้านเหมือนเดิม ส่วนฟิลด์ใหม่ `personnel_type` ใช้เฉพาะบัญชีหลังบ้านเพื่อแยกบุคลากรภายในองค์กรออกจากบุคลากรภายนอก

- `internal`: บุคลากรภายในองค์กร
- `external`: บุคลากรภายนอกที่ได้รับสิทธิ์ใช้ระบบหลังบ้าน

บัญชีพนักงานเดิมจะมีค่าเป็น `internal` โดยอัตโนมัติ ผู้ดูแลระบบเป็นผู้กำหนดและแก้ไขประเภทบุคลากร เจ้าของบัญชีแก้ไขเองไม่ได้

## การเข้าถึงหน้า

ส่วนรูปประจำตัว ชื่อ แผนก และรหัสพนักงานด้านล่างของแถบเมนูจะกดได้ และนำไปยังหน้า “บัญชีของฉัน” ปุ่มออกจากระบบยังคงอยู่ตำแหน่งเดิมเพื่อไม่เปลี่ยนพฤติกรรมที่ผู้ใช้คุ้นเคย

หน้าและ API ของบัญชีต้องตรวจสอบเซสชันพนักงานทุกครั้ง รหัสผู้ใช้ต้องได้จากเซสชันฝั่งเซิร์ฟเวอร์ ห้ามรับรหัสผู้ใช้จากหน้าจอเพื่อเลือกบัญชีหรือประวัติ

## ส่วนติดต่อผู้ใช้

### แท็บข้อมูลบัญชี

แสดงรูปตัวอักษรย่อ ชื่อ นามสกุล สถานะบัญชี ประเภทบุคลากร รหัสพนักงาน แผนก ตำแหน่ง สิทธิ์ อีเมล และเบอร์โทรศัพท์

- ชื่อ นามสกุล รหัสพนักงาน แผนก ตำแหน่ง สิทธิ์ ประเภทบุคลากร และสถานะ เป็นข้อมูลอ่านอย่างเดียว
- บุคลากรภายในดูอีเมลได้แต่แก้ไขไม่ได้
- บุคลากรภายนอกแก้ไขอีเมลได้
- บุคลากรทั้งสองประเภทแก้ไขเบอร์โทรศัพท์ได้
- เมื่อบันทึกสำเร็จ ต้องปรับข้อมูลเซสชันที่แสดงในแถบเมนูให้ตรงกับฐานข้อมูล

### แท็บความปลอดภัย

- เปลี่ยนรหัสผ่านด้วยรหัสผ่านปัจจุบัน รหัสผ่านใหม่ และการยืนยันรหัสผ่านใหม่
- แสดงวันและเวลาเข้าสู่ระบบล่าสุดเป็นเวลาประเทศไทย
- มีปุ่มออกจากระบบ
- ไม่แสดงหรือบันทึกรหัสผ่านเดิมและรหัสผ่านใหม่ลงในประวัติ

### แท็บประวัติการทำงานของฉัน

แสดงเฉพาะรายการที่ `user_id` ตรงกับผู้ใช้ในเซสชันปัจจุบัน ตารางประกอบด้วยวันและเวลา ประเภทกิจกรรม โมดูล รหัสรายการที่เกี่ยวข้อง และรายละเอียด

ตัวกรองประกอบด้วยช่วงวันที่ โมดูล และประเภทกิจกรรม ได้แก่ เพิ่ม แก้ไข ลบ อนุมัติ ปฏิเสธ เปลี่ยนสถานะ และความปลอดภัย ผลลัพธ์แบ่งหน้าและเรียงจากใหม่ไปเก่า

รวมกิจกรรมเข้าสู่ระบบ เปลี่ยนรหัสผ่าน และรีเซ็ตรหัสผ่าน แต่ไม่แสดงกิจกรรมออกจากระบบหรือรายการเซสชันภายในระบบ วันที่และเวลาทั้งหมดส่งพร้อมเขตเวลาและแสดงเป็นเวลาประเทศไทย

## การบันทึกประวัติ

ใช้ตาราง `emp_activity_logs` ที่มีอยู่แล้วเป็นแหล่งข้อมูลหลัก และเพิ่มกลไกบันทึกกิจกรรมจากคำขอแก้ไขข้อมูลที่สำเร็จของผู้ใช้หลังบ้าน

- บันทึกเฉพาะคำขอ `POST`, `PUT`, `PATCH` และ `DELETE` ที่ตอบกลับด้วยสถานะสำเร็จ
- ระบุผู้กระทำจากเซสชันพนักงานเท่านั้น
- ระบุประเภทกิจกรรม โมดูล รหัสรายการ และคำอธิบายที่ไม่เก็บข้อมูลลับ
- ป้องกันการบันทึกซ้ำในจุดที่มีการเขียนประวัติเดิมอยู่แล้ว
- การเรียก API เดิมโดยไม่มีเซสชันยังคงมีพฤติกรรมเดิม เพื่อจำกัดผลกระทบของงานนี้ แต่จะไม่ถูกผูกเป็นประวัติของพนักงานคนใด

การสร้างประวัติจะอยู่ในธุรกรรมเดียวกับการแก้ข้อมูลเมื่อจุดเดิมรองรับธุรกรรม หากไม่รองรับ กลไกส่วนกลางจะบันทึกหลังคำขอสำเร็จโดยไม่ทำให้คำขอหลักล้มเหลวเมื่อระบบประวัติมีปัญหา

## กระบวนการลืมรหัสผ่าน

1. ผู้ใช้เลือก “ลืมรหัสผ่าน” ในหน้าเข้าสู่ระบบและกรอกรหัสพนักงานหรืออีเมล
2. ระบบตอบกลับด้วยข้อความแบบเดียวกันไม่ว่าพบบัญชีหรือไม่ เพื่อป้องกันการเดาบัญชี หากข้อมูลตรงกับบัญชีหลังบ้านที่ใช้งานอยู่ ระบบจะสร้างรหัสคำร้องสำหรับแสดงผล พร้อมโทเคนลับที่เก็บเฉพาะในเบราว์เซอร์เดิม
3. ผู้ดูแลระบบเห็นจำนวนคำร้องที่รอดำเนินการและเปิดดูรายละเอียดในส่วนจัดการพนักงาน ซึ่งแสดงชื่อ รหัสพนักงาน ประเภทบุคลากร แผนก และเบอร์โทรเดิมจากฐานข้อมูล
4. ผู้ดูแลโทรกลับไปยังเบอร์โทรเดิมที่แสดงจากฐานข้อมูล ห้ามใช้เบอร์ใหม่ที่ผู้ขอแจ้งระหว่างกระบวนการ ผู้ขอต้องแจ้งรหัสคำร้องให้ตรงกับรายการที่ผู้ดูแลเห็น
5. เมื่อตรวจสอบตัวตนและรหัสคำร้องตรงกัน ผู้ดูแลเลือกอนุมัติ หากติดต่อไม่ได้ ข้อมูลไม่ตรง หรือมีข้อสงสัย ให้ปฏิเสธพร้อมบันทึกเหตุผล
6. หน้าเดิมตรวจสอบสถานะเป็นช่วง ๆ เมื่ออนุมัติจะแสดงแบบฟอร์มตั้งรหัสผ่านใหม่
7. ผู้ใช้ตั้งรหัสผ่านใหม่ ระบบยกเลิกเซสชันเดิมทั้งหมด ปิดคำร้อง และบันทึกกิจกรรมรีเซ็ตรหัสผ่าน

ผู้ดูแลระบบไม่เห็น ไม่กำหนด และไม่รับรหัสผ่านใหม่ สิทธิ์อนุมัติมีเฉพาะบัญชีที่มีบทบาท `admin` คำร้องผูกกับเบราว์เซอร์ที่สร้างคำร้อง ใช้ได้ครั้งเดียว และหมดอายุ 30 นาทีหลังอนุมัติ หากปิดแท็บหรือโทเคนหาย ผู้ใช้ต้องสร้างคำร้องใหม่ วันเกิด คำถามลับ เลขบัตรประชาชน และเลขท้ายโทรศัพท์ไม่ใช้เป็นหลักฐานหลักในการอนุมัติ

## โครงสร้างฐานข้อมูล

เพิ่มคอลัมน์ในตาราง `users`:

- `personnel_type`: ข้อความที่ยอมรับเฉพาะ `internal` หรือ `external` สำหรับบัญชีหลังบ้าน โดยบัญชีเดิมใช้ `internal`

เพิ่มตาราง `employee_password_reset_requests`:

- รหัสหลักของคำร้อง
- รหัสอ้างอิงที่แสดงแก่ผู้ใช้
- รหัสผู้ใช้ที่ขอรีเซ็ต
- แฮชของโทเคนเบราว์เซอร์ โดยไม่เก็บโทเคนจริง
- สถานะ `pending`, `approved`, `rejected`, `used` หรือ `expired`
- วันเวลาที่สร้าง วันหมดอายุหลังอนุมัติ วันเวลาอนุมัติ และวันเวลาใช้งาน
- รหัสผู้ดูแลที่ตัดสินคำร้องและเหตุผลการปฏิเสธ

เพิ่มดัชนีสำหรับรหัสอ้างอิง รหัสผู้ใช้ สถานะ และวันสร้าง เพื่อรองรับการค้นหาและจำนวนคำร้องรอดำเนินการ

## API

กลุ่ม API บัญชีพนักงานที่ต้องมีเซสชัน:

- อ่านข้อมูลบัญชีปัจจุบัน
- แก้ไขอีเมลหรือเบอร์โทรตามประเภทบุคลากร
- เปลี่ยนรหัสผ่าน
- อ่านประวัติของตนเองพร้อมตัวกรองและการแบ่งหน้า

กลุ่ม API รีเซ็ตรหัสผ่าน:

- สร้างคำร้องจากหน้าเข้าสู่ระบบ
- ตรวจสถานะด้วยโทเคนของเบราว์เซอร์
- ตั้งรหัสผ่านใหม่หลังคำร้องได้รับอนุมัติ
- อ่านรายการและจำนวนคำร้องสำหรับผู้ดูแลระบบ
- อนุมัติหรือปฏิเสธคำร้อง โดยตรวจบทบาท `admin` ฝั่งเซิร์ฟเวอร์

การตอบกลับต้องใช้ข้อความที่ไม่เปิดเผยว่ารหัสพนักงานหรืออีเมลใดมีอยู่ในระบบ เพื่อลดการเดาบัญชีจากหน้าเข้าสู่ระบบ

## การจัดการข้อผิดพลาด

- ตรวจรูปแบบอีเมล เบอร์โทร และความแข็งแรงของรหัสผ่านทั้งหน้าจอและเซิร์ฟเวอร์
- ปฏิเสธการแก้อีเมลของบุคลากรภายใน แม้มีการเรียก API โดยตรง
- ปฏิเสธการอ่านประวัติของผู้ใช้อื่น
- ปฏิเสธการอนุมัติจากผู้ใช้ที่ไม่ใช่ผู้ดูแลระบบ
- แสดงสถานะคำร้องหมดอายุ ถูกปฏิเสธ หรือถูกใช้แล้วอย่างชัดเจน
- การกดอนุมัติหรือส่งแบบฟอร์มซ้ำต้องไม่สร้างผลลัพธ์ซ้ำ

## การทดสอบ

### ฝั่งเซิร์ฟเวอร์

- การย้ายฐานข้อมูลกำหนดบัญชีพนักงานเดิมเป็นบุคลากรภายใน
- บุคลากรภายในแก้อีเมลไม่ได้ แต่แก้เบอร์โทรได้
- บุคลากรภายนอกแก้อีเมลและเบอร์โทรได้
- การเปลี่ยนรหัสผ่านตรวจรหัสเดิมและยกเลิกเซสชันอื่น
- API ประวัติคืนเฉพาะข้อมูลของผู้ใช้ในเซสชัน
- กิจกรรมเพิ่ม แก้ไข ลบ อนุมัติ และเปลี่ยนสถานะถูกบันทึกโดยไม่ซ้ำ
- เฉพาะผู้ดูแลระบบอนุมัติหรือปฏิเสธคำร้องได้
- หน้าผู้ดูแลแสดงเฉพาะเบอร์โทรเดิมจากฐานข้อมูลและบันทึกผลการโทรยืนยันก่อนอนุมัติ
- โทเคนผิด เบราว์เซอร์ผิด คำร้องหมดอายุ และคำร้องใช้ซ้ำถูกปฏิเสธ
- ไม่มีรหัสผ่านหรือโทเคนจริงปรากฏในฐานข้อมูลและผลลัพธ์ API

### ฝั่งหน้าจอ

- การกดข้อมูลพนักงานในแถบเมนูเปิดหน้าบัญชี
- สิทธิ์แก้ไขฟิลด์เปลี่ยนตามประเภทบุคลากร
- แท็บประวัติใช้ตัวกรอง แบ่งหน้า และแสดงเวลาไทยถูกต้อง
- กระบวนการขอรีเซ็ตเปลี่ยนสถานะจากรออนุมัติไปยังตั้งรหัสผ่านใหม่
- เมนูคำร้องและการอนุมัติแสดงเฉพาะผู้ดูแลระบบ
- สถานะโหลด สำเร็จ ไม่พบข้อมูล และข้อผิดพลาดแสดงผลครบ

## สิ่งที่ไม่รวมในงานนี้

- การส่งอีเมล SMS หรือการแจ้งเตือนผ่านบริการภายนอก
- การแก้ชื่อ นามสกุล รหัสพนักงาน แผนก ตำแหน่ง สิทธิ์ หรือประเภทบุคลากรโดยเจ้าของบัญชี
- การแก้ไขหรือสร้างผู้กระทำย้อนหลังให้ประวัติที่ไม่มีรหัสผู้กระทำ
- การปรับระบบสิทธิ์ของ API เดิมทั้งโครงการ นอกเหนือจาก API ใหม่และการตรวจบทบาทสำหรับคำร้องรีเซ็ตรหัสผ่าน
